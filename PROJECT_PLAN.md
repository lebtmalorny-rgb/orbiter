# Общий план развития Orbiter

> Этот файл — единая дорожная карта проекта и журнал прогресса. Перед началом
> крупного этапа создаётся отдельная спецификация и подробный implementation
> plan в `docs/superpowers/`; после проверки этапа обновляются статус, дата и
> краткий результат в таблице ниже.

**Цель:** превратить текущий прототип в понятное локальное приложение, которое
явно разделяет учебную RK4-модель, real-time SGP4/UTC, 3D-орбиту и ground track,
не смешивает системы координат и устойчиво работает с кэшем CelesTrak.

**Архитектурное направление:** Python остаётся источником SGP4-распространения
и HTTP API. Браузер отвечает за состояние интерфейса и Three.js-рендеринг, но
получает единый контракт траектории с явными frame, time scale, units и source.
Монолитный `orbiter_web.html` постепенно разделяется на небольшие ES-модули без
удалённых runtime-зависимостей.

**Технологии:** Python 3.9+, NumPy, Skyfield/SGP4, plain HTML/CSS/JavaScript,
Three.js, pytest, ruff и Playwright для браузерной проверки.

## Порядок выполнения

### Этап 1. Контракт траектории и регрессионная база

Сначала необходимо описать единый объект траектории, который можно использовать
для RK4, SGP4 и будущего импорта. Минимальные поля контракта:

- `id`, `name`, `source` и `kind`;
- `frame`, `time_scale`, `units` и `force_model`;
- `epoch_utc`, `generated_at_utc`, `cache_status` и `epoch_status` там, где они
  применимы;
- упорядоченные `samples` с явным временем;
- раздельные координаты для инерциальной 3D-орбиты и Earth-fixed/ground-track
  представления — без составления одного шестимерного state из разных frames.

Критерии готовности:

- pytest проверяет сериализацию, единицы, порядок времени и обязательные поля;
- тест запрещает объединять Earth-fixed position с GCRS velocity;
- README и `guide.md` используют те же определения frame/time/units;
- существующие manual и SGP4 сценарии продолжают запускаться.

### Этап 2. Модульная структура frontend

Разделить текущий `orbiter_web.html` по ответственности, сохранив plain
HTML/CSS/ES modules и локальные assets. Целевая граница модулей:

```text
orbiter_web.html              каркас первого viewport и точки монтирования UI
assets/css/orbiter.css        layout, панели, responsive и состояние режимов
assets/js/app.js              композиция приложения и верхнеуровневые события
assets/js/model.js            контракт и проверка траекторий
assets/js/dynamics.js         учебные orbital elements и RK4
assets/js/realtime-client.js  HTTP-запросы и нормализация SGP4 payload
assets/js/playback.js         model/live/paused cursor и интерполяция
assets/js/scene.js            Three.js objects, layers, camera и rendering
assets/js/ui.js               элементы меню, status и mode-specific controls
assets/js/catalog.js          локальные presets до перехода на API каталога
```

Разделение выполняется небольшими переносами без одновременного изменения
физики. После каждого переноса manual mode проверяется офлайн, а SGP4 mode — на
валидном кэше.

Критерии готовности:

- в inline `<script type="module">` нет бизнес-логики;
- каждый модуль имеет одну ответственность и явные exports;
- нет новых npm/CDN-зависимостей;
- desktop/mobile сцена и управление визуально не регрессировали.

### Этап 3. Логическое разделение интерфейса

Верхний уровень меню получает два режима: `Учебная орбита` и `SGP4 / UTC`.
Общие настройки камеры и слоёв остаются около сцены; параметры орбитальных
элементов, RK4 и J2 показываются только в учебном режиме; каталог, эпоха, кэш и
live controls — только в SGP4 режиме.

В real-time режиме отдельно выбирается визуальный слой:

- `3D-орбита` — инерциальное положение из согласованного frame;
- `Трасса над Землёй` — WGS84/Earth-fixed представление;
- при необходимости оба слоя можно показать одновременно, но с разными
  цветами, легендой и семантикой.

Критерии готовности:

- пользователь по одному экрану понимает активную модель и источник данных;
- неактивные параметры не могут незаметно переключить режим;
- видны маркеры `начало окна`, `сейчас`, прошлый и будущий участки;
- первый viewport по-прежнему занят Землёй и спутником, а домашний вид находится
  над Москвой: `55.7558° N`, `37.6173° E`.

### Этап 4. Геометрия и системы координат

Для 3D-орбиты использовать положение и скорость из одной инерциальной системы.
Для ground track использовать Earth-fixed/WGS84 pipeline и не называть его
замкнутой орбитой. Текущая сферическая Земля остаётся явно документированной
статичной визуальной опорой до отдельного точного Earth-fixed этапа.

Критерии готовности:

- один период 3D-орбиты не получает искусственный разрыв от вращения долготы;
- crossing ±180° не создаёт длинной ложной линии;
- тесты проверяют непрерывность, радиус, допустимые latitude/longitude и frame;
- HUD не вычисляет физические величины из координат разных frames.

### Этап 5. Время, playback и качество линии

Ввести явную state machine для model time и wall-clock UTC. Обновление GP/OMM
данных не должно само снимать пользовательскую паузу или переносить paused
cursor. В real-time режиме нужна отдельная команда `Вернуться к текущему UTC`.

Шаг распространения, частота анимации и плотность геометрии разделяются. Для
линий задаётся ограничение на угловое расстояние/сагитту либо выполняется
адаптивное досэмплирование, чтобы прямые Three.js-сегменты не уходили к Земле.

Критерии готовности:

- `Стоп` остаётся паузой после автообновления;
- `Сброс` имеет отдельную, документированную семантику для manual и SGP4;
- возврат вкладки из background синхронизирует только live cursor;
- тест с редкой исходной сеткой не допускает визуального провала сегмента ниже
  заданного порога.

### Этап 6. Кэш, stale и offline

Хранить metadata кэша рядом с payload: время успешной загрузки, URL/query,
формат и статус последней попытки. Сохранить TTL 2 часа и fallback на последний
валидный payload. Для HTTP 301/403/404 добавить persistent cooldown/backoff,
чтобы приложение не повторяло заведомо неуспешный запрос в цикле.

Критерии готовности:

- UI отдельно показывает возраст загрузки и возраст element epoch;
- stale/offline состояние заметно без открытия подробной OMM-панели;
- устаревшие элементы не выдаются за гарантированно точный real-time результат;
- transient network error использует последний валидный кэш;
- тесты подтверждают отсутствие повторных запросов во время backoff.

### Этап 7. API и каталог

Вынести разбор и проверку `duration_min`/`step_seconds` в общий helper, сохранив
документированные HTTP clamps `1..1440` минут и `1..600` секунд, а также общий
лимит `MAX_TRAJECTORY_SAMPLES`. Ошибки пользовательского ввода должны давать
4xx, а не общий 500.

UI постепенно переводится с hardcoded списка на `/api/realtime/catalog`, не
создавая отдельных сетевых запросов для каждого спутника.

Критерии готовности:

- pytest покрывает границы, NaN/Infinity, sample limit и HTTP status;
- CelesTrak URL по-прежнему содержит явный `FORMAT=JSON`;
- один запрос группы обслуживает каталог без N+1 downloads;
- каталог показывает NORAD ID, epoch status и cache source.

### Этап 8. Проверки и сопровождение

Каждый этап обязан завершаться следующими командами:

```powershell
venv\Scripts\python.exe -m ruff check .
venv\Scripts\python.exe -m pytest
git diff --check
```

Для изменений браузера дополнительно запускается локальный сервер и Playwright:

```powershell
venv\Scripts\python.exe third.py --no-browser --port 8770
```

Проверяются desktop и mobile viewport, пустая/непустая WebGL-сцена, console
errors, локальные assets, manual offline mode, SGP4 cached mode, live/paused и
stale/offline сценарии. Screenshots, traces, `.playwright-mcp/`, `.serena/`,
`.orbiter_cache/` и другие tool artifacts не коммитятся.

## Дальнейшее расширение

После стабилизации одной траектории можно добавлять несколько именованных
спутников, независимую видимость и focus/HUD, затем импорт JSON/CSV и OEM-like
эпhemerides. Точный Earth-fixed режим с TEME/GCRS → ITRF/ECEF → WGS84 и EOP
планируется последним: он не должен блокировать исправление текущего смешения
frames и UX.
